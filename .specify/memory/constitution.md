# Hackathon Todo – Phase II Constitution

This document defines the non-negotiable constitutional rules that govern ALL specifications, agents, and implementations for Phase II: Todo Full-Stack Web Application.

**This constitution overrides all other instructions.**

Any agent or implementation that violates this constitution is considered INVALID.

---

## PROJECT IDENTITY

**Project Name**: Hackathon Todo – Phase II
**Repository Type**: Monorepo
**Development Model**: Spec-Driven + Agentic Development
**Manual Coding Policy**: STRICTLY PROHIBITED

All code MUST be generated by agents operating from specs.

---

## Core Principles

### I. Spec Authority

Specs are the single source of truth. Code MUST follow specs exactly. If a behavior is not specified, it MUST NOT be implemented. Specs define WHAT, never HOW.

**Spec Hierarchy**:
1. `/sp.constitution` (this file)
2. `/specs/overview.md`
3. `/specs/features/*`
4. `/specs/api/*`
5. `/specs/database/*`
6. `/specs/ui/*`

**Rationale**: Centralized authority prevents scope creep, ensures traceability, and maintains alignment between design and implementation.

### II. Scope Boundary (Phase II Only)

**Allowed Scope**:
- Multi-user Todo Web Application
- REST API backend
- Persistent database storage
- JWT-based authentication
- Responsive web UI

**Explicitly Forbidden**:
- Chatbots
- AI assistants
- MCP tools
- Phase III or Phase IV features
- Admin or superuser roles

**Rationale**: Clear boundaries prevent feature creep and ensure Phase II delivers a focused, testable product increment.

### III. Technology Stack (Mandatory)

**Frontend**:
- Next.js 16+ with App Router
- TypeScript
- Tailwind CSS
- Better Auth (JWT enabled)

**Backend**:
- FastAPI (Python)
- SQLModel ORM
- REST architecture only

**Database**:
- Neon Serverless PostgreSQL
- Cloud-first design
- No embedded or file-based databases

**Authentication**:
- Better Auth issues JWT tokens
- JWT passed via Authorization header (Bearer token)
- Session cookies forbidden
- Ownership enforced at database query level

**Rationale**: Standardized stack ensures consistency, reduces complexity, and leverages proven cloud-native patterns.

### IV. API Architecture

- All endpoints live under `/api/*`
- RESTful semantics required
- No GraphQL
- No RPC-style endpoints

**Allowed Operations**:
- Task CRUD (Create, Read, Update, Delete)
- Task completion toggle

**Disallowed Operations**:
- Cross-user queries
- Bulk operations without user scope
- Admin-level access

**Rationale**: REST provides predictable, cacheable, stateless communication. Scope restrictions enforce single-user isolation.

### V. Database Integrity

- `tasks` table MUST include `user_id` column
- Index required on `tasks.user_id`
- Foreign key integrity enforced
- No implicit cascading deletes

**Rationale**: User isolation at the database layer is the final line of defense. Indexes ensure query performance under multi-user load.

### VI. UI Security & Responsiveness

- Authentication required before task access
- UI must never display another user's data
- Responsive design required (mobile and desktop)
- Backend is the final authority (UI cannot override security rules)

**Rationale**: Client-side validation is convenience; server-side enforcement is security. Responsive design ensures accessibility.

### VII. Agent Conduct

**Spec Writer Agent**:
- May create and update specs
- May NOT write code

**Architecture Planner Agent**:
- May design system architecture
- May NOT expand feature scope

**Database / Backend / Frontend Agents**:
- May implement specs only
- May NOT reinterpret or invent requirements

**Integration Tester Agent**:
- May report violations
- May NOT silently fix by changing behavior

**Rationale**: Role separation ensures checks and balances. Agents must stay within their domain of authority.

### VIII. Change Control

- Any change requires spec update FIRST
- Spec changes must be explicit and versioned
- Breaking changes must be documented

**Rationale**: Prevents implementation drift from design. Maintains traceability and auditability.

---

## Success Criteria (Phase II)

Phase II is complete ONLY when:

1. All specs are implemented
2. All APIs are JWT secured
3. User isolation is enforced end-to-end
4. Frontend and backend operate independently
5. All acceptance tests pass
6. System is deployable to production

**Measurable Gates**:
- No cross-user data leakage in any scenario
- API responds with 401 for unauthenticated requests
- API responds with 403 for unauthorized access attempts
- UI handles authentication errors gracefully
- Database queries include `user_id` filter for all user-scoped operations

---

## Governance

This constitution supersedes all other practices, guidelines, and preferences. No agent, developer, or stakeholder may override these principles without formal amendment.

**Amendment Procedure**:
1. Proposed change documented with rationale
2. Impact analysis performed across all specs and code
3. Approval required before implementation
4. Version number incremented according to semantic versioning
5. Migration plan created for affected artifacts

**Compliance Verification**:
- All PRs/reviews must verify compliance with this constitution
- Any complexity introduced must be explicitly justified
- Constitution violations are blocking issues

**Versioning Policy**:
- MAJOR: Backward incompatible governance/principle removals or redefinitions
- MINOR: New principle/section added or materially expanded guidance
- PATCH: Clarifications, wording, typo fixes, non-semantic refinements
